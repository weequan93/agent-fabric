# G0 owner recovery order

Recover from the latest trusted owner checkpoint. Checkpoints are supplied to privileged owner APIs; model content and untrusted client snapshots never grant restore or dispatch authority. G0 models these protocols in memory. Durable crash journals, authenticated deployment storage and operator permissions require G1 qualification.

1. Load current server identity, Space membership, source/destination grants, server payer, policy revisions and deletion tombstones. An unavailable authority or revoked grant stops restoration and adapter calls. Historical grants never replace current grants. Apply artifact/outbox tombstones before reading old payloads; an older manifest cannot resurrect a deleted artifact.
2. Restore operation records and the budget checkpoint into fresh owners. Validate the complete checkpoint before committing any row. Keep immutable operation, Run, payer, reservation and receipt identities. Interrupted `dispatched` operations become `unknown`. Never downgrade an existing unknown/terminal operation to prepared. Budget recovery preserves settled receipts, remaining ceiling and conserved balances; every unresolved reserved row becomes unknown. BudgetLedger refuses live checkpoint rollback.
3. Restore the session's committed contiguous events using the pure reducer. Replay has no model, execution, clock or billing port and must cause zero provider calls, external writes or new settlements. Current read authorization is checked before exposing replayed state. Preserve local unsent drafts separately; reconnect never submits a draft or replays disconnected input.
4. Reconcile unknown effects by their original operation identity. Use a registered controlled executor's lookup and original receipt. A found receipt settles the original reservation once. A proven safe absence permits a safe-failure receipt. An unresolved outcome remains explicit waiting with a domain owner/human resolver and retained reservation. Do not redispatch unknown operations or release unknown usage to regain allowance.
5. Only after all pending effects are resolved may the session iterate. Recheck current actor/payer/source rights, policy revision, exact approval, accepted artifact digest, lease expiry and task/Run/runtime generations. A different effect requires a new operation and exact current approval. A model adapter restarted with an unknown reservation cannot invoke again even if its volatile result cache is empty.
6. Budget exhaustion records `waiting: budget`, resolver and next action. An authorized ceiling administrator may top up the same allowance with a current revision. Read/spend authority alone cannot raise ceilings. Reauthorization and reserve still precede the next invocation; top-up does not clear an unknown effect.
7. Stop advances fences before requesting termination. Keep cancellation, quarantine and unknown external outcomes explicit. It cannot undo an already sent effect. Stop-run leaves other attempts' authority intact; Stop-task blocks implicit admission. A runtime replacement uses a new identity and credentials. Desktop disconnect fences old input; return requires the observed current driver, reconciliation and a fresh lease. Shared-computer conflicts wait for the existing owner rather than creating an extra computer.
8. Completion comes from the controller's current required checks and applicable confirmed delivery, not a model completion claim. Notification is separate: failed notification does not undo an accepted artifact or confirmed effect. Behavior rollback never restores source grants, fact memories or deletion tombstones.

The workflow fault suite verifies revocation, authority outage, old fence, expired lease, cross-Space dispatch, deleted artifacts, denied top-up and unknown model usage with observed adapter call counts.

Archive, suspend/terminate and delete have separate semantics. Archive retains execution/storage and their fees. Suspend/terminate stops compute charges while retaining storage and unknown/settled obligations. Delete adds current tombstones and stops retained-storage fees; it never erases the financial ledger or legitimizes a blind retry.

## Unknown model usage and session continuation

The Session must persist its model operation and reservation identity before awaiting the trusted model port. An unconfirmed result, rejection or interrupted call leaves that identity pending and fences both subsequent model calls and effect dispatch. The pure event history carries the pending model across a fresh restore; a live restore cannot erase or rewrite an already observed event prefix.

The trusted server supplies `SessionPorts.modelOperation` to bind the actual model operation/reservation and `modelResolution` to read the original current owner record. A current-authorized ledger lookup can prove pre-invocation absence/release or original settlement. An exception code, top-up, a caller's claimed outcome or a different receipt cannot clear pending usage. `SessionLoop.resolveModel` uses that trusted lookup and exact identity; completed reconciliation requires the original nonempty receipt. Unknown stays pending without a provider retry. Recheck current authority after asynchronous lookup before recording any resolution. A legacy successful text-returning model port retains its API, while rejection without a trusted resolution fails closed.
